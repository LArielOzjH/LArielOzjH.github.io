Why another blog

The goal is not to build a news feed. The goal is to keep durable research notes: small derivations, architecture readings, experiment logs, and paper summaries that still make sense six months later. A good note is compact enough to scan but precise enough to recover the reasoning behind an experiment.

Reading structure

Long technical writing benefits from explicit landmarks. The table of contents on the left should remain quiet most of the time. As the reader scrolls, only the current section needs to become darker and receive a bullet. That gives orientation without turning the page into a dashboard.

The right side has a different job. It should behave like a margin: notes appear near the paragraph they annotate and move with the article. This is closer to how Thinking Machines uses numbered notes and citations. A sidenote can be short, but it must be close enough that the reader does not lose the thread.

In practice, mixed prose needs small optical corrections. A CJK span can be scaled slightly down and raised by a small relative offset so that Chinese characters sit more naturally next to Latin ascenders and x-height. This is not a semantic distinction; it is a typesetting correction.

A tiny scaling-law sketch

where (N) is model size and (D) is amount of data. 这不是完整结论，只是用来检查公式排版、行高和中英文混排。The useful part of writing this down is not the equation itself, but the reminder that every term hides an experimental protocol.

Interpreting the terms

Constants matter because they encode how a measurement was made. A note should record conditions explicitly:

  • Which data distribution was used?
  • Was the model trained to convergence or stopped at a fixed compute budget?
  • Which optimizer, batch size, precision, and schedule were used?
  • Were measurements taken before or after compilation warmup?
  • Did wall-clock time include data loading, checkpointing, and evaluation?

2 The same scaling-law equation can describe experiments that feel completely different in practice because memory traffic or cross-device communication dominates wall-clock time.

Two runs can share a clean curve and still feel completely different in practice.2 One may be FLOP-bound and easy to scale; another may spend most of its time on memory movement, kernel launch overhead, or collective communication.

What should be written down

When the note is about hardware or training systems, I want the experimental record to preserve at least three layers of context:

  1. The mathematical claim or performance question.
  2. The implementation path used to test it.
  3. The operational detail that might invalidate an overly clean interpretation.

That ordering matters. If the observation starts with a single number, it is easy to forget what the number means. If it starts with the question, the number has a place to land.

Numbered protocol

For experiment-heavy posts, numbered protocol is clearer than bullets when order matters:

  1. Define the baseline configuration: exact commit, checkpoint, dataset slice, and hardware.
  2. Change one variable at a time, even if interactions between variables seem obvious.
  3. Save raw logs before compressing the result into a table or figure.
  4. Write a short interpretation while the run is still fresh.
  5. Revisit that interpretation after the next comparison run.

The point is not bureaucracy. The point is preventing a common failure mode: remembering the conclusion while forgetting the path that made the conclusion believable.

Failure notes

Failure notes deserve their own section. In research engineering, negative results often become the most useful artifact because they constrain the next experiment. A good failure note includes symptom, suspected cause, and the smallest test that could falsify the suspicion.

Useful failure records often include small details:

  • If a training run diverges, record the first unstable metric and the step where it appears.
  • If throughput drops, separate dataloader time, kernel time, and communication time.
  • If a result improves, check whether the improvement survives a second seed or a smaller sanity run.
  • If a cache or compilation artifact changes the result, write down how the run was warmed up.

A local debugging pattern

When debugging a system result, I usually want the note to keep two voices separate. The first voice states what happened. The second voice states what I think it means. 混在一起之后，后面回看很容易把猜测误认为事实。

For example:

  1. Observation: throughput dropped from 410k tokens/s to 355k tokens/s after changing sequence packing.
  2. Hypothesis: padding distribution changed enough to alter attention kernel occupancy.
  3. Test: replay the same batch shapes with the old packing path.
  4. Result: if the replay remains slow, investigate kernels; if it recovers, investigate data path.

This small structure prevents a note from becoming a pile of impressions.

Figure placement

Images should be close to the text that uses them. A figure that arrives too early feels decorative; a figure that arrives too late forces the reader to hold context in memory. For this site, image placement should be conservative: one image near the opening, one near a method or result, one near a closing reflection if it helps the page breathe.

Third-level heading

Sometimes a section needs one more layer, but the table of contents does not need to expose every small local heading. A third-level heading should create rhythm inside the prose without becoming a top-level landmark. The reader should be able to skim the article by second-level sections and then use third-level headings only when already inside a section.

Citation and source discipline

Not every note needs formal citations, but every technical claim should make it possible to recover the source. When a claim comes from a paper, the note should link the paper. When a claim comes from an experiment, the note should link config, log, or script. When a claim is personal interpretation, the text should say so.

Source checklist

Before publishing a note, I want to check:

  1. Are all quoted numbers tied to a source, run, or derivation?
  2. Are assumptions separated from observations?
  3. Are links placed near the claims they support?
  4. Would I understand this note after a month away from the project?
